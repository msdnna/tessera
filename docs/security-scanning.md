# Сканы безопасности (SAST/SCA)

Как устроены проверки безопасности в репозитории, что делать с находками и почему
гейт работает как храповик, а не как «ноль находок».

Введено задачами #2936 (backend/frontend + CodeQL), #2937 (SonarQube-стенд),
#2938 (Android/desktop), #2939 (храповик, скилл, этот документ).

## Одна точка входа

```bash
make scan-tools          # поставить сканеры в tools/bin (пинованные релизы + sha256)
make scan-backend        # govulncheck + gosec
make scan-frontend       # osv-scanner по frontend/yarn.lock
make scan-secrets        # gitleaks по рабочему дереву
make scan-android        # detekt (SARIF) + osv-scanner по зависимостям Gradle
make scan-desktop        # osv-scanner по desktop/src-tauri/Cargo.lock
make scan                # всё сразу
```

Всё это — обёртки над `tools/security-scan.sh`, чтобы Makefile, CI и ночной агент
звали ровно одно и то же. Отчёты кладутся в `reports/security/*.sarif`
(gitignored). SARIF — потому что его умеют все четыре тула и его же ест
code-scanning GitHub.

**Отсутствующий тул — это ошибка, а не пропуск.** Скан, который молча ничего не
просканировал и вышел с нулём, хуже отсутствия скана. `SCAN_ALLOW_MISSING=1`
ослабляет это до предупреждения — только для отладки.

## Храповик вместо «ноль находок»

На дереве сегодня ~150 находок, и их триаж — отдельная работа. Гейт «ноль
находок» покрасил бы `develop` в красный в первый же день и был бы выключен на
второй. Поэтому текущее состояние заморожено в **`tools/security-baseline.json`**,
а правило — как у храповика русских литералов во фронтенде: **список может
сокращаться, но не расти**.

Сравнение делает `tools/security-ratchet.py`, его запускает сам
`security-scan.sh` в конце каждого скана — отдельную команду звать не нужно.

Находка опознаётся по тройке **(тул, правило, где)** и **считается**, а не
привязывается к строке: номера строк уезжают от любой правки выше по файлу, а
базовая линия, которая шумит на несвязанных правках, быстро перестаёт
обновляться. «Где» — это файл для кодовых находок и **имя пакета** для
зависимостей, намеренно **без версии**: бамп всё ещё уязвимой зависимости не
должен выглядеть как новая проблема.

Счётчик важен: если в файле было 13 находок `G115`, четырнадцатая тоже станет
ошибкой.

### Два класса тулов

| Класс  | Тулы                        | Новая находка | Исчезнувшая находка |
|--------|-----------------------------|---------------|---------------------|
| `code` | gosec, detekt, gitleaks     | **падает**    | **падает** — нужно обновить базовую линию |
| `deps` | govulncheck, osv-scanner    | предупреждает | молча уйдёт при следующем обновлении |

Разделение не косметическое. `code`-тулы детерминированы относительно дерева:
новая находка там — это то, что принёс текущий коммит. `deps`-тулы читают ленту
advisory, которая меняется каждый день: новая находка обычно означает «кто-то
опубликовал CVE», а не «ветка сломалась», и красить чужой PR в красный за это
нельзя. Поэтому по умолчанию они шумят, а не падают:

```bash
SCAN_RATCHET_DEPS=fail make scan-backend   # если нужно жёстко
```

Исчезнувшая `code`-находка — тоже ошибка: если оставлять протухшие записи,
файл перестаёт описывать дерево, и следующей настоящей регрессии никто не
поверит. У `deps` withdrawn/rescoped advisory — норма, поэтому там только
сообщение.

### Исключение: достижимость govulncheck

Ровно ради этого govulncheck и стоит вместо обычного скана lock-файла: он
говорит, **вызывается ли** уязвимый символ из нашего кода. Это свойство дерева,
а не ленты advisory, — и оно ломало общее правило. Все находки govulncheck
указывают на один и тот же `go.mod`, поэтому по тройке (тул, правило, где) они
неотличимы: advisory, перешедшая из «просто в графе сборки» в «вызывается»,
сохраняла тот же ключ, счётчик не двигался, и храповик оставался зелёным именно
на том изменении, ради которого он заведён.

Теперь достижимые находки несут в ключе суффикс `[called]`:

```
"GO-2026-4918 go.mod [called]": 1     # вызывается из нашего кода
"GO-2026-5005 go.mod": 1              # только в графе сборки
```

Два состояния — два разных ключа, поэтому переход виден. Правила:

| Событие | Что делает храповик |
|---------|---------------------|
| Известная advisory стала вызываться | **падает** даже в режиме `warn` — это сделал коммит |
| Новая advisory пришла сразу вызываемой | предупреждает — коммит ни при чём, лента опубликовала CVE |
| Advisory перестала вызываться | сообщение «no longer reached» (это улучшение, не новая находка) |

Первая строка — единственное место, где `deps`-тул падает без
`SCAN_RATCHET_DEPS=fail`.

`make scan-backend` заодно печатает разбивку в сводке:

```
govulncheck: 46 finding(s): error=15, note=24, warning=7, 15 reached from our code
```

Триажить в первую очередь нужно эти 15, а не все 46.

### Обновить базовую линию

После того как находка починена (или осознанно принята):

```bash
make scan-baseline-update                      # перегенерировать всё
make scan-baseline-update SCAN_TARGET=backend  # только backend-тулы
```

Обновление **сливается**, а не перезаписывает файл целиком: прогон одного
компонента не стирает записи остальных. Диффы `tools/security-baseline.json`
коммитятся вместе с изменением и читаются на ревью — именно этот диff
показывает, что реально изменилось в безопасности.

Руками файл не правим: единственный способ убрать запись — прогнать скан и
увидеть, что находки больше нет.

### Подавить находку gosec в коде

Только `#nosec`, **не** `//nolint:gosec`:

```go
tr.TLSClientConfig = &tls.Config{InsecureSkipVerify: true} // #nosec G402 -- opt-in for self-hosted private CAs
```

Грабли, на которые мы уже наступили: `//nolint:gosec` здесь не работает **ни в
одном** из наших тулов. Мы гоняем gosec отдельным бинарём, а он про синтаксис
`//nolint` не знает; golangci-lint его понимает, но gosec у него не включён
(`backend/.golangci.yml` — `standard` + gocritic/revive/misspell). То есть такой
комментарий читается как «находка разобрана», а на деле не подавляет ничего и
она возвращается в базовую линию при каждом прогоне.

Правило — код (`G402`) и причина после `--` обязательны; аннотация действует на
свою строку или на следующую за ней. `#nosec` понимает и standalone-бинарь, и
gosec внутри golangci-lint, так что форма остаётся рабочей, если мы его туда
когда-нибудь включим.

Подавление — для осознанно принятого поведения. Если находку просто ещё не
разобрали, её место в базовой линии, а не под `#nosec`.

### Ручки

| Переменная | Значение |
|------------|----------|
| `SCAN_RATCHET=0` | не сравнивать с базовой линией вообще |
| `SCAN_RATCHET_UPDATE=1` | перезаписать базовую линию по этому прогону |
| `SCAN_RATCHET_DEPS=fail` | новые advisory тоже роняют прогон |
| `SCAN_FAIL_ON=any` | падать от самого факта находок (не гейт, а способ посмотреть) |
| `SCAN_ALLOW_MISSING=1` | отсутствующий тул — предупреждение |

## Что чем покрыто

| Компонент | SAST | SCA |
|-----------|------|-----|
| backend   | gosec | govulncheck (с reachability) |
| frontend  | CodeQL в CI (semgrep на этом хосте не ставится) | osv-scanner по `yarn.lock` |
| android   | detekt (SARIF) | osv-scanner по резолву `releaseRuntimeClasspath` |
| desktop   | clippy `-D warnings` в `make lint-desktop` | osv-scanner по `Cargo.lock` |
| весь репо | gitleaks по рабочему дереву | — |

Отдельные решения, чтобы не переоткрывать их заново:

- **`cargo audit` не берём**: релизных бинарей нет, то есть на каждой машине и в
  CI это `cargo install` с компиляцией ~200 крейтов. RustSec публикуется в OSV,
  так что те же advisory приходят через уже пинованный osv-scanner.
- **gitleaks ходит только по рабочему дереву** (`dir`), не по истории:
  переписывание истории не рассматривается, поэтому находка в старом коммите —
  это задача «ротировать креденшл», а не то, что может починить гейт. Разовый
  аудит истории — `gitleaks git .` руками, намеренно не сделан make-целью.
- **На Android сканируется только то, что уезжает в APK.** Gradle пишет в
  `verification-metadata.xml` вообще всё, что разрешил билд, включая собственный
  плагин-класспас — первый прогон дал 94 находки, и все до единой были CVE в
  инструментах сборки. `tools/gradle-deps-filter.py` сужает список до
  `releaseRuntimeClasspath` (183 артефакта из 751). Остальное — отдельная
  поверхность (supply chain машины сборки), решение по ней принимается явно.

## CI

- Джоб **Security** гоняет `scan-backend scan-frontend scan-secrets scan-desktop`
  и публикует SARIF в code scanning.
- Android-половина живёт в джобе **Android**: detekt — это Gradle-таска, а список
  зависимостей берётся резолвом конфигурации, то есть нужны JDK и SDK, которых в
  Security-джобе нет. SARIF оттуда публикуется под **своей категорией**
  (`sast-sca-android`) — при одинаковой категории джоб, закончивший последним,
  молча затёр бы находки другого.
- **CodeQL** — отдельный workflow (`.github/workflows/codeql.yml`), Go + JS/TS.
- Храповик в CI включён по умолчанию: падение джоба означает либо новую находку,
  либо непрокоммиченное обновление базовой линии.

## SonarQube

Стенд поднимается по требованию и в гейт не входит — это витрина качества, а не
блокирующая проверка: `make sonar-up` → `make sonar-token` → `make sonar-scan`
(детали — `deploy/sonarqube/README.md`).

## Разработка: когда гонять

Перед сабмитом изменения гоняем скан **затронутого компонента** — это дешевле
полного `make scan` и ловит ровно то, что мог принести коммит. Для агентной
разработки порядок описан в скилле `.claude/skills/tessera-security-scan/`.
