- **fix(api): скачанный файл снова приходит со своим именем (#2932).**
  Заголовок `Content-Disposition` собирался двумя способами. Экспорт документа шёл через
  общий хелпер, но тот кодировал `filename*` через `url.PathEscape` — а это кодирование
  для сегмента URL, не для `ext-value` (RFC 8187). Расходятся они ровно на трёх символах
  (`:`, `=`, `@`), которые `PathEscape` оставляет сырыми и которые не входят в `attr-char`.
  Любой из них в заголовке документа делал заголовок непарсящимся целиком, так что клиент
  не получал имени вообще — терялся и ASCII-фолбэк: документ «Смета: Q4» выгружался
  безымянным, а двоеточие в заголовке — обычное дело. Остальные три маршрута скачивания
  (вложение задачи, вложение чата созвона, запись созвона) клеили заголовок вручную через
  `fmt.Sprintf("attachment; filename=%q", …)`: сырые UTF-8 байты в `quoted-string`, который
  получатель по RFC 6266 читает как ISO-8859-1, то есть русское имя приезжало кракозябрами,
  а перенос строки `%q` превращал в литеральные `\n` внутри имени. Теперь все четыре
  маршрута зовут один `contentDisposition(name)` с процентным кодированием по `attr-char`;
  имя без единого пригодного символа даёт голый `attachment` вместо пустого `filename=""`.
  Веб и Android именуют файл сами и затронуты не были — чинится то, что видят curl, PAT-скрипты
  и сторонние клиенты. Тест round-trip'ит заголовок через `mime.ParseMediaType`, а храповик
  по исходникам пакета не даёт маршруту снова собрать заголовок руками. Прежний
  `TestContentDispositionSurvivesCyrillic` убран: он проверял заголовок подстроками, ни разу
  его не разбирая, — на замере он прошёл и на сломанной сборке, то есть ровно через него
  ошибка и дожила; все его утверждения перекрыты новым round-trip'ом.
