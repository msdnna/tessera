# changelog.d — фрагменты changelog

Чтобы фича-ветки **не конфликтовали** на `CHANGELOG.md` и `VERSION`, запись о changelog
не редактирует общий файл, а кладётся сюда отдельным файлом, привязанным к номеру задачи.
Сборка в общий `CHANGELOG.md` и бамп версий делаются **на `develop`** (см. ниже).

## Что делает фича-ветка

Один файл на задачу (можно несколько, если задача трогает разные компоненты):

```
changelog.d/<component>/<task#>[-slug].md
```

- `<component>` — `backend` | `frontend` | `android` | `desktop` | `mcp` (подпапка).
- `<task#>` — номер задачи Tessera (для родительской ветки — обычно номер родителя;
  можно и по подзадачам). Имя файла завязано на номер → фрагменты разных задач
  **физически не конфликтуют** при merge.

Содержимое = готовый markdown-буллет(ы) в стиле существующего CHANGELOG:

```markdown
---
bump: patch
---
- **fix(web): комментарии — «подпрыгивание» при отправке (#2612).**
  Опциональные детали с отступом в две пробела — как в текущих записях.
```

- Frontmatter `bump:` (`patch`|`minor`|`major`) **необязателен** — по умолчанию уровень
  выводится из conventional-типа первого буллета: `feat` → `minor`, `feat!`/`...!:` →
  `major`, всё остальное (`fix`/`perf`/`refactor`/…) → `patch`. Указывай `bump:` явно,
  только если нужно переопределить.
- Фича-ветка **VERSION и CHANGELOG.md НЕ трогает** — только добавляет фрагмент.

Скелет фрагмента можно создать хелпером:

```bash
make changelog-add TASK=2620 COMP=backend        # + опц. BUMP=minor SLUG=ws-auth
```

## Что делает develop (сборка релиза)

После merge веток, уже на `develop`:

```bash
make changelog-release            # собрать все компоненты с фрагментами
make changelog-release DRY=1      # показать план, ничего не меняя
make changelog-release ONLY=backend,frontend
```

Скрипт `tools/changelog-release.py` для каждого компонента с фрагментами:
1. вычисляет уровень бампа = максимум по его фрагментам, поднимает `VERSION`
   (через `tools/bump-version.sh`, у desktop он же правит `Cargo.toml`);
2. вставляет новую версию `### [x.y.z] — ДАТА` сверху нужной секции `CHANGELOG.md`
   (android → `## x.y.z — ДАТА` в `android/CHANGELOG.md`), собрав буллеты из фрагментов
   по возрастанию номера задачи;
3. удаляет собранные фрагменты.

Затем — обычный `chore(release): …` коммит на `develop` (push/tag делает пользователь).

## Почему так

`CHANGELOG.md`, `VERSION` и файлы миграций — точки сериализации, где конфликтует каждая
ветка. Фрагменты убирают конфликт по changelog полностью (уникальное имя на задачу), а
перенос бампа/сборки на `develop` — по `VERSION`. Миграции остаются последовательными
(`golang-migrate` линеен): номер занимаем **перед самым merge**, а задачи разбираем так,
чтобы миграционные шли после безмиграционных — тогда параллельных номеров почти не
возникает.
